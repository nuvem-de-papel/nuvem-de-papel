1. Plataforma e ambientes 6 ramos
Aplicação — como roda
  • Next.js 14.2.16 (App Router) · React 18 · TypeScript SSR dinâmico (force-dynamic nas telas do painel); CSS próprio em src/app/globals.css com tokens de identidade (paleta v3 cinza).
  • Server Components + Server Actions Telas buscam dado direto no Supabase (createAdminClient); mutações via server actions com validação no servidor.
  • Build de produção na Vercel vercel.json define 3 crons diários; deploy de produção nasce do push da main.
Repositórios
  • nuvem-de-papel (este) branch staging = homologação · branch main = produção (merge só com aprovação explícita).
  • nuvem-de-papel-documentacao roadmap enterprise, pareceres e documentação de decisão.
Ambientes
  • Homologação (staging) deploy da branch staging; banco Supabase de homologação (ref urlfwxeflxpdmmxkuuur).
  • Produção nuvemdepapel.com.br (alias *.vercel.app protegido por login Vercel); banco Supabase (ref cbnmnpnpioukbzircmzn).
Banco de dados
  • Supabase (PostgreSQL + Auth) service role no servidor; RLS/tenant por tenant_id; RPCs security definer para operações críticas (vendas, estoque, financeiro).
  • Multi-tenancy tenant fixo 00000000-0000-0000-0000-000000000001 no E2E; toda query do painel filtra por tenant_id.
Gates de mudança — obrigatórios
  • Códigolint → type-check → build → suíte e2e — zero falhas.
  • Bancopor migration: preflight → migration → pgTAP → smoke comportamental → build. Em produção, antes do merge.
  • Produçãomerge staging → main só com aprovação do dono do projeto.
  • CIGitHub Actions roda lint/type-check/build em todo push.
Estrutura de código
  • src/approtas (páginas, actions, APIs).
  • src/componentsconsoles e componentes de UI (AdminShell, PageHeader, consoles de cada módulo).
  • src/libregras de negócio, RBAC, Supabase, validações (ex.: documento.ts, crm.ts, rbac.ts).
  • supabase/migrations40 migrations 0001–0040, cada uma com preflight/test/rollback ao lado quando crítica.
  • e2esuítes Playwright + helpers (_*.cjs, fora da chain).
  • AGENTS.md + docs/regras permanentes de sessão e documentos de governança (este mapa).
2. Segurança e acesso (RBAC) 4 ramos
Middleware — src/middleware.ts
  • Matcher (áreas protegidas) /crm/* /configuracoes/* /logistica/* /pdv/* /financeiro/* /compras/* /vendas/* /email/* /portal/*
  • Cadeia de verificação sessão Supabase → perfil existe → perfil ativo → papel permitido no módulo. Fail-closed: sem env, 503; sem perfil/papel, 403; sem sessão, redirect /login.
Papéis — src/lib/rbac.ts
  • master gerente operador vendedor fornecedor revenda
  • Hierarquiamaster gerencia todos; gerente gerencia operador/vendedor/fornecedor/revenda (nunca master/gerente).
Matriz por módulo
  • Gestão master · gerente/configuracoes /financeiro /compras /vendas /email
  • Operacional + operador · vendedor/crm /logistica /pdv
  • Externo/portal/fornecedor → só fornecedor.
Trilha de auditoria
  • audit_logações de gestão (usuário criado/desativado, vendas, configurações) — leitura em /configuracoes/auditoria.

9. Convenções de governança 3 ramos
Quando atualizar ESTE mapa
  • Rota nova, renomeada ou removida
  • Módulo novo no painel ou na loja
  • Tabela ou view nova/renomeada no banco
  • Cron, webhook ou integração nova/removida
  • Papel novo ou mudança na matriz RBAC
Como atualizar
  • 1.Edite o ramo afetado neste arquivo (docs/mapa-estrutural.html).
  • 2.Incremente a versão e a data no topo (chip vX.Y).
  • 3.Adicione linha no changelog abaixo.
  • 4.Commite junto com a mudança estrutural que motivou a atualização.
Regras permanentes de sessão
  • Nunca commitar.gitignore alheio · nuvem-de-papel.code-workspace · segredos (chaves Supabase, Mercado Pago, CRON_SECRET).
  • Produçãoritual de migration antes do merge; merge na main só com aprovação explícita.
  • Saída de comunicaçãoestilo TDAH: próxima ação na 1ª linha, listas curtas, sem cortesias.
